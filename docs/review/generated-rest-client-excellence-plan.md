# Generated REST Client Excellence Plan

Started: 2026-08-26

Completed: 2026-08-26

Scope correction: provider specifications are authoritative. This plan evaluates and hardens the six
pinned clients currently in the repository; it does not require speculative validation of malformed
future OpenAPI releases. Provider defects remain generated, tested, and documented rather than being
corrected in the source pipeline.

## Objective

Turn the current generated REST clients and shared transport into a durable foundation for a future
abstraction API. The generated layer must remain a direct representation of each provider contract;
the future abstraction layer, not this layer, will own cross-provider normalization.

Completion means the implementation satisfies every measurable gate in this plan and a fresh review
under `docs/review/` finds no unresolved current-corpus correctness, determinism, cancellation,
fidelity, or package isolation defect.

## Non-goals

- No common repository, issue, pull request, pagination, authentication, retry, or error-body model.
- No invented provider behavior where an upstream specification is incomplete.
- No automatic retry policy in the core transport.
- No large provider-module split unless measurements show that subpath exports are insufficient.
- No public rename without a checked compatibility record and explicit review.
- No provider source correction or semantic normalization.
- No proactive requirement to reject or repair malformed future provider specifications. New
  snapshots are reviewed when they are introduced.

## Design invariants

1. All providers expose the same mechanical shape: constructor, `.rest`, grouped input, request
   options, and discriminated response envelope.
2. Provider operation names, wire names, paths, media types, schemas, statuses, and headers remain
   provider-native.
3. Generated static types agree with default runtime serialization and parsing for every emitted
   branch.
4. Every asynchronous request stage observes one native `AbortSignal` and preserves native abort
   identity.
5. Generation from pinned normalized inputs is deterministic, atomic, complete, and does not rewrite
   provider declarations.
6. Each provider can be imported without loading unrelated provider registries.
7. Raw Fetch escape hatches remain available when a provider specification is incomplete.

## Iteration protocol

Every defect class follows the same closed loop:

1. Record an exact failing current-corpus count or add a fixture for observed current behavior.
2. Make the smallest change at the layer that owns the invariant.
3. Run focused tests until green.
4. Regenerate all six providers from pinned normalized inputs.
5. Compare generated bytes, operation counts, public names, and diagnostics.
6. Run full format, lint, type-check, test, generation-freshness, and graph-freshness gates.
7. Re-run the current-corpus audit and update review evidence under `docs/review/`.
8. Continue only when the iteration has zero unexplained drift.

A test that merely snapshots incorrect output is not a gate. Each fixture must assert semantic wire
behavior, static type behavior, or an explicit diagnostic.

## Deterministic evidence tracked after every iteration

- expected provider set: Azure DevOps, Bitbucket, Codeberg, Gitea, GitHub, and GitLab;
- exact operation count and one-to-one input/response/metadata/method coverage;
- exact generated bytes from pinned normalized inputs;
- public operation/type name manifest;
- exact current provider-limitation diagnostic manifest;
- response media decoder/type mismatch count;
- unserializable request media count;
- conditional-required loss count;
- unresolved reference and silently dropped operation/parameter/response count;
- per-provider import dependency graph;
- full test/check/lint/format status.

## Iteration 0: make generation self-policing

### Changes

- Add fixture-driven generator tests covering schema composition, parameters, request media,
  response status/media/headers, servers, collisions, and current diagnostic policies.
- Add a whole-corpus invariant audit for the six expected providers and one-to-one generated shape.
- Add `generate:check` that renders into isolated staging, formats there, and byte-compares against
  `src/generated/`.
- Render and validate every provider before replacing any generated output.
- Reject every missing or unexpected provider. Generation is intentionally whole-corpus only, so no
  partial mode can produce a mixed or incomplete public surface.
- Emit deterministic diagnostics for limitations present in the pinned provider inputs and check the
  reviewed diagnostic baseline.

### Exit gate

- Generation failure cannot leave a mixed tree or delete a provider.
- Pinned inputs reproduce every generated byte.
- Every current provider limitation appears in a reviewed deterministic diagnostic manifest.

## Iteration 1: response contract and parsing

### Changes

- Generate explicit decode metadata per documented media representation.
- Decode JSON as schema data, textual representations as strings, binary/opaque representations as
  `Blob` or a deliberately selected streaming type, and no-content responses as `undefined`.
- Match documented status/media before parsing; define missing and unexpected `Content-Type`
  behavior without falsely claiming a documented branch.
- Select default `Accept` from successful response representations before error-only media.
- Remove unsafe parse overrides from typed generated methods while retaining them on the raw
  transport.
- Distinguish abort, transport, parse, documented HTTP, and undocumented-response failures.
- Add documented-success narrowing and a typed unwrap that rejects undocumented responses.

### Exit gate

- Response decoder/type mismatch count is zero.
- JSON, text, vendor text, binary, multipart, empty, malformed, default, and undocumented fixtures
  agree at runtime and compile time.
- All successful binary/text operations advertise a compatible default `Accept` value.

## Iteration 2: request serialization

### Changes

- Serialize top-level JSON `null` as JSON bytes while preserving `undefined` as no body.
- Correct Gitea release attachment octet-stream generation.
- Separate raw request binary from FormData-compatible binary fields.
- Correctly serialize every query/path/header style advertised by the current six providers.
- Apply configured global query consistently to generated and raw requests.
- Add wire fixtures for JSON, nullable JSON, text, URL encoded, multipart, octet-stream, Blob,
  bytes, and streams.

### Exit gate

- Every request media branch currently emitted by all six providers has a passing serialization
  fixture.
- Every current serializable request branch has a passing wire fixture.
- Provider-declared branches forbidden by native Fetch remain generated and appear as exact tested
  limitations rather than being removed from the specifications.

## Iteration 3: cancellation, ownership, and error semantics

### Changes

- Pass request context, including `AbortSignal`, to lazy headers/auth and hooks with a compatible
  callback transition.
- Observe or race cancellation before and after every awaited request stage.
- Define response-body and stream ownership.
- Prevent caller mutation of configured base URL, headers, and query defaults.
- Define and test operation-server credential forwarding.
- Preserve original abort reason and make parse errors carry operation/response context.

### Exit gate

- Pre-abort and abort during auth, before-request hook, Fetch, after-response hook, parsing, and
  stream use are deterministic and prompt.
- `AbortSignal.timeout()` works without a second timeout system.
- Abort, transport, parse, HTTP, and undocumented outcomes remain distinguishable.

## Iteration 4: schema and metadata fidelity

### Changes

- Preserve branch-dependent `required` constraints through `oneOf` and `anyOf` composition.
- Use a lossless `int64` policy: safe integers remain numbers, unsafe JSON integers become `bigint`,
  and bigint request values serialize as exact JSON numeric tokens.
- Preserve typed response-header contracts alongside native `Headers`.
- Emit exact-key deeply readonly operation registries and a deliberate runtime immutability policy.
- Audit the current inputs for unresolved references and silently dropped operations, parameters, or
  responses; require an exact zero-loss result.
- Split request/response schema projection when read-only/write-only semantics demand it.

### Exit gate

- Conditional-required loss count is zero.
- Unsafe `int64` values round-trip exactly in JSON, path, and query fixtures.
- Registry typos fail type-checking and nested runtime metadata cannot be mutated under the selected
  policy.
- Response headers are discoverable and typed without replacing native `Headers`.

## Iteration 5: public compatibility and package isolation

### Changes

- Check a reviewed public name manifest during every regeneration.
- Reserve Promise-like, runtime import, TypeScript utility, and global names.
- Keep accepted existing names stable when new upstream collisions appear.
- Add `./rest` and one public package subpath per provider while retaining the aggregate root.
- Add import-graph tests proving a provider subpath does not load unrelated provider modules.
- Measure startup, editor, and type-check behavior before deciding whether provider internals need
  further splitting.

### Exit gate

- No unexplained public rename.
- Each provider and shared transport imports independently through declared package exports.
- Larger module topology changes occur only with recorded measurements.

## Iteration 6: provider contract review

For each provider, exercise representative authentication headers, pagination form,
rate-limit/continuation headers, uploads, downloads, documented errors, undocumented responses, and
operation-level servers. Upstream omissions remain provider-specific diagnostics and documentation;
they do not become fabricated common models.

### Exit gate

- Every accepted upstream limitation is explicit.
- Every supported provider behavior has at least one deterministic wire fixture.
- No fix introduces cross-provider semantic normalization.

## Final excellence review

After all iterations, create a new evidence-based review in `docs/review/` rather than editing the
original findings into apparent success. The final review must:

- rescan the full generated corpus;
- compare every original finding with current evidence;
- report remaining diagnostics by provider;
- include exact gate commands and results;
- report generated size, operation counts, name changes, and import isolation;
- declare `excellent` only when every current-corpus exit gate above passes.

If any gate fails, add the current-corpus failure as the next loop item, fix it, regenerate, and
repeat the final review. Work stops at zero unexplained current correctness or determinism defects.
